Architecture writing fails when the reader cannot tell a decision from a description, or a measured
number from a hopeful one. The components below exist to make those distinctions structural instead of
stylistic.

## Callout

Four semantic variants. Each carries a text label, so meaning never depends on colour.

<Callout type="info">Context the reader should know before continuing.</Callout>

<Callout type="warning">A pitfall that will cost time or data if ignored.</Callout>

<Callout type="important">The point of the section, if the reader remembers only one thing.</Callout>

<Callout type="assumption">
  A number used to reason about a design — e.g. *"assume 400 tenants with 25 % active at peak"* — that
  is **not** a measurement.
</Callout>

```mdx
<Callout type="assumption" title="Design assumptions">…</Callout>
```

## ADR

An Architecture Decision Record card. In case studies, `<ADR id="MT-ADR-001" />` renders a recorded
decision from YAML; in articles every field can be passed inline:

<ADR
  id="EX-ADR-001"
  title="Use the transactional outbox for domain events"
  status="accepted"
  date="2026-10-01"
  context="Services must publish events when their state changes. Writing to the database and publishing to the broker are two separate operations that can fail independently."
  decision="Write the event to an outbox table in the same transaction as the state change; a relay publishes outbox rows to the broker and marks them sent."
  alternatives={[
    { option: "Publish after commit", summary: "Commit, then publish from application code.", rejectedBecause: "A crash between the two loses the event permanently." },
    { option: "Distributed transaction (2PC)", summary: "Coordinate the database and broker with XA.", rejectedBecause: "Poor support in modern brokers, couples availability of both systems." }
  ]}
  consequences={{
    positive: ["No lost events: state and event commit atomically", "The broker can be unavailable without blocking writes"],
    negative: ["Delivery becomes at-least-once — consumers must be idempotent", "An extra table and relay process to operate"]
  }}
  risks={["Outbox table growth if the relay stalls"]}
  followUps={["Alert on outbox age (oldest unpublished row)"]}
/>

## Diagrams as code: Mermaid and D2

and an invalid source fails the build with the parser's error. The source stays one click away.

## Writing guidelines

1. **Label provenance** in frontmatter: `illustrative`, `sanitized`, `experimental` or
   `production-derived`.
2. **Never present an assumption as a result.** Use `<Callout type="assumption">` for inputs and show
   the arithmetic.
3. **Pair every visual with text.** Diagrams require a `description`; explorers ship a catalogue.
4. **Record decisions as ADRs**, including what was given up.
