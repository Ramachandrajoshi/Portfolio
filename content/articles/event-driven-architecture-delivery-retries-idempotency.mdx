Moving from synchronous calls to events removes temporal coupling — services no longer need each other
to be up at the same time. In exchange, every message can now be **lost, duplicated, delayed or
reordered**. Reliable event-driven systems are not the ones that prevent those outcomes; they are the
ones in which those outcomes are harmless.

## Delivery semantics, honestly

| Guarantee | What it really means | Typical cost |
| --- | --- | --- |
| At-most-once | May lose messages, never duplicates them | Lost business events |
| At-least-once | Never loses messages, may duplicate them | Consumers must be idempotent |
| "Exactly-once" | Usually: exactly-once *within one broker's transaction scope* | Vendor-specific; ends at side effects |

The effect you care about — a card charged once, a parcel shipped once — happens **outside** the
broker. So the practical target is **at-least-once delivery with idempotent effects**: effectively-once.

## Step 1: never lose the event (transactional outbox)

Writing to the database and then publishing to a broker are two operations that can fail
independently. The outbox makes them one:

Note the deliberate consequence: a crash between *publish* and *mark as published* re-publishes the
event. The outbox converts "maybe lost" into "maybe duplicated" — a trade you want, because duplicates
can be made harmless and losses cannot be undone.

## Step 3: order only where it matters

Global ordering serialises the whole system. Most domains need order **per aggregate** — "cancel"
after "place" for the same order — and nothing across aggregates. Partition by the aggregate id and
each order's events land on one partition, consumed in sequence. Carry an aggregate **version** in
every event so a consumer can detect, and park, an event that arrives early after a replay.

Classify errors first: **transient** (timeouts, 429s, a dependency restarting) go through delayed retry
topics with jitter — 1 minute, 10 minutes, 1 hour. **Permanent** errors (invalid data, a bug) go
straight to a dead-letter topic with the error and attempt history. And when a dependency is down for
hours, a **circuit breaker** should pause consumption rather than churn messages through retries.

<Callout type="warning" title="A dead-letter queue nobody watches is a data-loss queue">
  Give every DLQ an owner, an alert on size and age, and a replay tool that preserves original message
  ids — so replays are safe by construction.
</Callout>

## Step 5: evolve without breaking consumers

Producers and consumers deploy independently, so the **schema is the contract**. Register schemas
and enforce compatibility in CI: additive, optional fields are fine; renames and type changes need a
new event type or version and a migration period.

## Checklist

- Is every state change published through an outbox (or CDC)?
- Is every consumer idempotent — including calls to external APIs?
- Which key gives ordering where the business needs it?
- Are transient and permanent failures handled differently?
- Does every DLQ have an owner, an alert and a replay path?
- Are outbox age and consumer lag on a dashboard?
