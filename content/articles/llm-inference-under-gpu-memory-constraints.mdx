When teams first serve an LLM on their own hardware, the surprise is rarely that the model is slow.
It is that **the GPU runs out of memory at a handful of concurrent users** — while the GPU's compute
sits mostly idle. This article explains why, and how to estimate capacity from a model's
configuration before running a single benchmark.

<Callout type="assumption" title="All numbers here are theoretical">
  The arithmetic below uses an 8B-class model (32 layers, 8 KV heads × 128 dimensions) on a 24 GB GPU.
  It shows the method and the orders of magnitude. Real engines add fragmentation, workspace and kernel
  overheads — always validate with a load test on your hardware.
</Callout>

## Three things compete for GPU memory

1. **Weights** — parameters × bytes per parameter. Fixed once loaded.
2. **KV cache** — the attention keys and values for every token of every active sequence. Grows with
   concurrency × context length.
3. **Runtime overhead** — CUDA context, activations, temporary workspace. Roughly fixed per process.

Whatever the weights and runtime don't use is the KV budget, and **the KV budget is your concurrency**.

## KV cache per token

For each token, every layer stores a key and a value vector for each KV head:

```text
KV bytes per token = 2 × layers × kv_heads × head_dim × bytes_per_element
                   = 2 × 32 × 8 × 128 × 2 B (FP16)
                   = 131,072 B ≈ 128 KiB
```

So one 8k-token conversation holds ~1 GB of KV cache. Grouped-query attention (8 KV heads instead of
32) is already doing a lot of work here: with full multi-head attention it would be 4× larger.

## Two phases, two bottlenecks

Generation has two phases with different limits — which is why "tokens per second" alone is a
misleading metric.

<Mermaid
  src="architecture/llm-inference-platform/diagrams/request-lifecycle"
  title="Request lifecycle: admission, prefill and decode"
  description="A streamed request is authenticated and admitted only if KV budget is available. The model server prefills the prompt, returns the first token, then decodes one token per step until done and releases its KV blocks; without budget the request is queued or rejected with 429."
/>

- **Prefill** processes the whole prompt in parallel. It costs roughly 2 × parameters FLOPs per prompt
  token and is mostly **compute-bound**. It determines **time to first token**.
- **Decode** produces one token per step for every sequence in the batch. Each step reads all weights
  (once for the whole batch) plus each sequence's KV cache, so it is mostly **memory-bandwidth-bound**.
  It determines **inter-token latency**.

A useful upper bound for a single stream is *memory bandwidth ÷ bytes read per token*: with ~1 TB/s
and 16 GB of FP16 weights, at most ~60 tokens/s; with 4-bit weights (~5 GB), at most ~200 tokens/s.
Batching amortises the weight reads, which is why **continuous batching** is the main throughput lever.

Generic leaderboard deltas rarely predict how a quantised model behaves on *your* structured

## Admission control: overload by design, not by accident

When too many long requests arrive, an engine that admits everything must **preempt** sequences —
evicting their KV cache and recomputing later. Throughput and latency collapse together. The
alternative is to admit by **token budget**: estimate prompt + max_tokens, and admit only if a replica
has that much free KV memory. Excess work queues by priority or receives a 429 with Retry-After —
explicit, observable, and fair.

<Callout type="warning" title="max_tokens is a memory reservation">
  Generous default `max_tokens` values reserve KV memory that is never used. Set defaults per workload
  from observed completion lengths.
</Callout>

## What to measure

- Time to first token and inter-token latency, **per priority class**.
- KV-cache utilisation, free blocks and **preemptions**.
- Queue wait, admitted vs rejected requests.
- Prompt and generated tokens per second; batch size distribution.
- Output validity (JSON, tool calls) as a cheap production quality signal.
