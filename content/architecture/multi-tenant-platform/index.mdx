## 1. Context and business problem

A B2B software product began life as a single-tenant application. Every new customer got their own
deployment: an application server, a database, configuration files and — over the years — a few
customer-specific patches. That model was simple when there were five customers. With many more, it
has become the main constraint on the business:

- **Releases fan out.** Shipping a fix means upgrading N separate stacks. In practice customers drift
  across several versions, and support has to reason about which bug exists where.
- **Configuration drift causes incidents.** The most common root cause in post-incident reviews is a
  difference between deployments, not a defect in the code.
- **Onboarding is a project.** Provisioning a new customer takes days of manual infrastructure work.
- **Cost grows linearly** with customers, while most customers use a small fraction of their stack.

The business wants **one platform, many tenants** — while keeping the property customers were
promised and are audited on: *their data is physically separate from everyone else's.*

## 2. Requirements and constraints

The constraints matter more than the requirements; they eliminate most of the design space.

| Constraint | Consequence for the design |
| --- | --- |
| Contracts promise physically separated customer data. | Shared tables with a `tenant_id` column are not acceptable as the primary isolation mechanism. |
| Some tenants require a specific region or dedicated hosting. | Tenant placement must be data (configurable per tenant), not code. |
| The product cannot be frozen during modernisation. | The migration must be incremental: legacy deployments and the new platform coexist for a long time. |
| Existing customer databases hold years of data. | Prefer *registering* existing databases over copying their data into a new structure. |
| The team knows .NET and PostgreSQL well. | Favour designs that fit the existing skills and operational tooling. |
| A small platform team operates everything. | Automate the per-tenant operations that become frequent: provisioning, migration, relocation. |

## 3. Functional and non-functional requirements

**Functional**

1. Serve every tenant from one shared, horizontally scaled application tier.
2. Bind every request and every background job to exactly one tenant before any data access.
3. Provision, suspend, relocate and decommission tenants through automated workflows.
4. Keep shared reference data (global configuration, feature definitions) in one place, with
   per-tenant overrides.
5. Support tenant-level backup and point-in-time restore.
6. Provide cross-tenant reporting for the vendor without live cross-database queries.

## 4. Quality attributes and acceptance criteria

The table above is the contract for the design. Three attributes dominate, and they pull against each
other:

- **Isolation** pushes towards *more* separation (separate databases, credentials, keys).
- **Operability** pushes towards *less* separation (fewer things to migrate, monitor and pay for).
- **Deployability** demands that releases do not wait for, or fail because of, individual tenants.

Every decision in this case study is a position on that triangle, and each one records which corner it
gives up.

## 5. Architecture and system boundaries

The system is split into two planes:

- The **control plane** answers *"who is this tenant, where does their data live, which version are
  they on, and are they allowed in?"* It consists of the tenant catalogue (PostgreSQL, highly
  available), a resolution cache (Redis) and a secret store.
- The **data plane** holds tenant data: one PostgreSQL database per tenant, placed on shared clusters
  (shards), reached through PgBouncer.

Between them sits a **stateless application tier** — the Platform API, background workers and a
migration orchestrator — that holds no tenant-specific state of its own. Tenancy becomes a row in the
catalogue rather than a deployment.

The boundaries that matter most are **trust boundaries**, not deployment boundaries: the edge (where
untrusted input arrives), the tenant-resolution middleware (where a request acquires a tenant), and
the data-access layer (where a tenant becomes a database connection).

The request pipeline that implements MT-ADR-002 is deliberately small. A sketch of the
resolution middleware:

```csharp
public sealed class TenantResolutionMiddleware(RequestDelegate next, ITenantDirectory directory)
{
    public async Task InvokeAsync(HttpContext http, TenantContextAccessor accessor)
    {
        // 1. The only trusted source of tenancy is the validated token.
        var claim = http.User.FindFirst("tid")?.Value;
        if (claim is null) { http.Response.StatusCode = 401; return; }

        // 2. The host must map to the same tenant — defends against token reuse across tenants.
        var tenant = await directory.FindAsync(TenantId.Parse(claim), http.RequestAborted);
        if (tenant is null || !tenant.Hosts.Contains(http.Request.Host.Host))
        {
            SecurityAudit.TenantMismatch(http, claim);
            http.Response.StatusCode = 403; return;
        }

        // 3. Lifecycle and schema-compatibility gates fail closed.
        if (tenant.Status != TenantStatus.Active || !SchemaWindow.Supports(tenant.SchemaVersion))
        {
            http.Response.Headers.RetryAfter = "120";
            http.Response.StatusCode = 503; return;
        }

        accessor.Set(TenantContext.From(tenant)); // immutable for the rest of the request
        await next(http);
    }
}
```

## 9. Trade-offs and rejected alternatives

Choosing database-per-tenant moves complexity rather than removing it. The trade-offs are explicit:

- **Migrations become a fleet operation.** Accepted, and contained by expand/contract and waves
  (MT-ADR-003). The price is that every breaking change takes two releases.
- **Connections become a capacity problem.** Accepted, and contained by PgBouncer and shard placement
  (MT-ADR-005). The price is giving up session-level PostgreSQL features on tenant connections.
- **Cross-tenant questions need a pipeline.** Accepted — a nightly, incremental, de-identified export
  is a feature for privacy, not just a workaround.
- **The catalogue is a new critical dependency.** Accepted, and contained by caching with
  *stale-if-error*: if the catalogue is unavailable, instances keep serving tenants they have already
  resolved for a bounded period, trading freshness of configuration for availability.

Two tempting ideas were rejected outright:

- **Lazy, on-request migrations** — they put DDL on the request path and turn an operator problem into
  a customer-visible one.
- **A "tenant" header chosen by the client** — it would move the isolation boundary into every
  authorisation check in the codebase.

## 10. Security and trust boundaries

Isolation is layered so that no single mistake leaks data:

1. **Identity.** The tenant comes only from a signed token claim, cross-checked against the host
   (MT-ADR-002). Mismatches are rejected and audited as security events.
2. **Context.** Resolution produces an immutable, request-scoped `TenantContext`; an endpoint filter
   fails closed if it is missing. Background jobs re-establish context from the message envelope and
   re-verify it against the catalogue.
3. **Data access.** Tenant repositories can only obtain a `TenantDbContext` from a factory that reads
   `TenantContext` (MT-ADR-004); architecture tests enforce the boundary.
4. **Credentials.** Each tenant database has its own role and credentials, issued from the secret store
   through workload identity. Even a resolution bug cannot use one tenant's connection to read another
   tenant's database.
5. **Storage.** Encryption at rest per database; premium tenants can have their own keys.
6. **Egress.** Exports to analytics are de-identified before leaving the data plane.

Threats considered explicitly: token replay across tenant hosts, tenant enumeration via error
messages (responses are uniform), privilege escalation through the provisioning workflow (separate
role, audited), and data leaks through logs (PII-scrubbing processor in the telemetry pipeline).

The general rule: **every shared resource has a per-tenant limit**, so failure and overload stay
attached to the tenant that caused them.

## 12. Scalability and performance reasoning

The interesting scaling limit is not CPU — the application tier scales horizontally — it is
**database connections**. A first-principles estimate shows why MT-ADR-005 is necessary.

<Callout type="assumption" title="Design assumptions — not measurements">
  The figures below are inputs chosen to reason about the design (400 tenants, 8 API instances,
  default-like client pools). They are not measurements of any real system. Real values come from the
  load test described in section 14.
</Callout>

**Without a pooler**, client pools multiply:

- 400 tenants × 8 instances × a pool of up to 10 connections = **32,000** potential connections.
- PostgreSQL uses a process per connection; practical `max_connections` per cluster is in the low
  hundreds before memory and context switching dominate.

**With PgBouncer in transaction mode**, server connections are bounded by what is *active*, not by
what is *configured*:

- Suppose at peak 25 % of tenants are active and each needs ~3 concurrent transactions:
  400 × 0.25 × 3 = **300** server connections across the fleet.
- Split over two shards, that is ~150 per cluster — inside a sensible budget, with headroom.
- Adding tenants means adding shards at a planned density, not raising `max_connections`.

This estimate also tells you *what to measure*: the ratio of active tenants at peak and transactions
per active tenant. If either is much higher than assumed, shard density must fall.

Two other scaling concerns:

- **Tenant resolution** happens on every request, so it must be a memory lookup in the steady state;
  the catalogue sees only cache misses and invalidations.
- **Migration duration** grows with the number of tenants, but no longer blocks releases. Waves run
  with bounded parallelism to avoid saturating any one shard.

## 13. Observability and operational considerations

- **Tenant-aware telemetry.** Traces and logs carry `tenant.id`; metrics carry `tenant.tier` and
  `shard` rather than the tenant id, to keep metric cardinality bounded. Exemplars link a slow metric
  bucket to a trace with the tenant id.
- **Per-tenant golden signals** for the largest tenants and per-shard signals for everyone else:
  request rate, error rate, p95 latency, PgBouncer queue wait, breaker state.
- **Fleet state is queryable.** "Which tenants are on which schema version, on which shard, in which
  status?" is a catalogue query, and a dashboard.
- **Runbooks as automation.** Relocating a tenant, re-running a failed migration and suspending a tenant
  are orchestrator commands with audit trails, not manual procedures.

## 14. Testing and validation strategy

| Risk | Test | When |
| --- | --- | --- |
| Cross-tenant data access | Isolation suite: two tenants provisioned in Testcontainers; every API endpoint called as tenant A with identifiers belonging to tenant B must return 403/404 and touch no B data. | Every build |
| Boundary erosion | Architecture tests for data-access contexts, forbidden `tenantId` parameters, direct connection construction. | Every build |
| Schema skew | Integration suite run against both N-1 and N schema versions. | Every build |
| Migration safety | Each migration applied to anonymised snapshots of the largest and oldest tenant schemas; duration and lock behaviour recorded. | Before each release |
| Noisy neighbour | Load test with a Zipf-distributed tenant mix plus one tenant at 10× load; verify the fairness criterion in section 3. | Before go-live, then monthly |
| Failure isolation | Chaos test: stop one tenant database and the catalogue primary in turn; verify the containment table above. | Before go-live, then quarterly |

## 15. Outcomes and lessons learned

**Outcomes.** This reference architecture has not been measured in production, so it claims no
results. Success would be demonstrated by the acceptance criteria in the quality-attribute table and
the validation plan above: zero isolation-suite failures, releases that no longer wait on migrations,
and noisy-neighbour behaviour within the fairness target under a skewed load test.

**Lessons — the reasoning I would carry into any similar system:**

- *Start from the promises already made to customers.* The isolation contract eliminated half the
  design space before any technology discussion.
- *Make tenancy data, not infrastructure.* Once placement, version and status are rows in a catalogue,
  most operational work becomes automatable.
- *Every shared resource needs a per-tenant limit.* Otherwise multi-tenancy turns one customer's bad
  day into everyone's.
- *Make boundaries executable.* Architecture tests are cheap compared with the cost of a cross-tenant
  incident discovered by a customer.
- *Do the capacity arithmetic early.* Connection count, not CPU, was the constraint — and a ten-line
  estimate revealed it before any load test.
